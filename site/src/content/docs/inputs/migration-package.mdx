A **migration package** is a folder or zip with everything for one unit of migration: usually one
ThoughtSpot worksheet/model plus the liveboards and answers built on it.

<FileTree>
- SALES-WS-001/
  - manifest.yaml optional; files are auto-detected without it
  - thoughtspot/
    - \*.table.tml
    - \*.sql_view.tml
    - \*.worksheet.tml or \*.model.tml
    - \*.liveboard.tml
    - \*.answer.tml
  - strategy/
    - model.yaml Mosaic model YAML export
    - dashboards/ one `.mstr` file per dashboard
  - mapping.yaml optional: deliberate renames and exclusions only
</FileTree>

## What developers export

| Input | Source | |
|---|---|---|
| ThoughtSpot TML **with dependencies** | UI "Export TML (with associated)" or `POST /api/rest/2.0/metadata/tml/export` with `export_associated: true` | <Badge text="Required" variant="danger" /> |
| Strategy model | `POST /api/model/dataModels/{id}/export` (YAML, Strategy April 2026+), or `GET /api/model/dataModels/{id}/{tables,attributes,factMetrics,metrics,hierarchy}` | <Badge text="Required" variant="danger" /> |
| Strategy dashboards | The dashboard's `.mstr` file (Share > Download Dashboard). Binary; read by the Strategy expert's `mstr_reader` (format and known gaps in its README) | <Badge text="If content migrated" variant="caution" /> |
| `mapping.yaml` | The developer, only for renames or intentional exclusions | <Badge text="Optional" variant="note" /> |

## Where packages and reports live

A package location is a string; its scheme picks how it is read. The same applies to where run folders go
(`INSPECTOR_RUNS_DIR`). Both ends are plug-in, so a host can add its own store without touching the agents.

| | Input: `validate {package: ...}` | Output: `INSPECTOR_RUNS_DIR` |
|---|---|---|
| Local | a folder or a `.zip` (under `PACKAGE_ROOT`), or `file://...` | a folder, e.g. `/runs` |
| S3 | `s3://bucket/prefix/` (a package folder) or `s3://bucket/key.zip` | `s3://bucket/prefix` |
| Anything else | `register_reader("<scheme>", fn)` in each agent that reads packages | `register_writer("<scheme>", fn)` in the Inspector |

With S3, every agent that reads the package downloads it itself, with its own AWS credentials (the runtime's
role on AgentCore): the Inspector reads `manifest.yaml` / `mapping.yaml`, the ThoughtSpot expert `thoughtspot/`,
the Strategy expert `strategy/`. So each role needs `s3:ListBucket` and `s3:GetObject` on the package prefix, and
the Inspector's role `s3:PutObject` on the reports prefix. `AWS_ENDPOINT_URL` points boto3 at an S3-compatible
store. Downloads are cached per content (S3 ETags) and published atomically. The full report also comes back in
the `validate` response, so a failed write to the reports location loses nothing.
