| Static result | Data result | Final status | Note |
|---|---|---|---|
| Proven equal | not needed | <Badge text="PASS" variant="success" /> | Canonical trees identical |
| Proven different | not run | <Badge text="FAIL" variant="danger" /> | |
| Proven different | data equal | <Badge text="FAIL (latent)" variant="danger" /> | E.g. INNER vs LEFT with no orphan rows *today*. `latent_policy: fail \| warn` (default `fail`) |
| LLM: equivalent | data equal | <Badge text="PASS (data-verified)" variant="success" /> | |
| LLM: equivalent | data differs | <Badge text="FAIL" variant="danger" /> | The data decides |
| LLM: not equivalent | data equal | <Badge text="PASS (data-verified)" variant="success" /> + advisory | The data decides; the edge case is noted |
| LLM: not equivalent | data differs | <Badge text="FAIL (confirmed)" variant="danger" /> | |
| Any | can't run / not allowed | <Badge text="UNVERIFIED" variant="caution" /> | Keeps the package from being READY |

<Aside type="note" title="Why a latent difference still fails by default">
	Matching data shows the numbers agree **on today's data**. A proven logic difference, like an
	INNER join where ThoughtSpot used LEFT, will produce different numbers as soon as an orphan row
	arrives. The client needs the numbers right from day 1, so the default is `fail`. It can be
	switched to `warn`.
</Aside>
