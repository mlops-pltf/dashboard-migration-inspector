## Fan-out: the classic Freeform SQL defect

One order worth 100 has three order lines. Both sides use the same formula on the same column:

## The rules

<Steps>
1. **Relation grain.** Physical tables: primary key from ThoughtSpot cardinality, Strategy attribute key forms, or a key-uniqueness probe. Derived relations: computed from the SQL. A one-to-many join makes the grain finer.

2. **Measure home grain.** The grain of the table the fact column belongs to (`orders.amount` → `order_id`).

3. **Fan-out (JN-04).** The measure is aggregated over a relation finer than its home grain → `SUM`, `COUNT` and `AVG` are inflated. `MIN`, `MAX` and `COUNT DISTINCT` are safe. **Blocker**, reported with the join that causes it.

4. **Chasm trap (JN-05).** Two facts with different home grains flattened into one relation through a shared dimension. **Blocker.**

5. **Join applicability (JN-06).** A ThoughtSpot measure resolved with progressive joins, while its Strategy counterpart sits in a Freeform SQL with INNER joins. Strategy drops orphan fact rows **even when the dimension isn't in the query**. **Blocker.**
</Steps>

<Aside type="tip" title="No guessing on unknown cardinality">
	When there's no cardinality metadata and no key form, Inspector asks the data agent for a key
	profile (`COUNT(*)` vs `COUNT(DISTINCT key)`, orphan counts) instead of assuming.
</Aside>
